# Architecture and state sequence

```mermaid
flowchart TD
  A[Presence qualification] --> B[Settle and sample]
  B --> C{Sensor decision}
  C -->|Known| D[Align selector]
  C -->|Ambiguous| E[Fault: hold item]
  D --> F[Release and close gate]
  F --> G[Home and wait clear]
  G --> A
```

The shared controller in `control.h` defines the same sequence used by the sketch. Startup is STOPPED. Arming with clear chamber/closed stop loop commands HOME, waits 700 ms, then requires absence for 300 ms before IDLE. IDLE requires presence for 150 ms; SETTLE waits 200 ms; SAMPLE collects ten readings at >=20 ms intervals.

Classification prioritizes a consistent metal signal, then uses the mean normalized moisture value for non-metal policy cases. Mixed metal votes and the moisture uncertainty band produce UNKNOWN/FAULT. During SETTLE/SAMPLE, loss of presence faults rather than releasing an unclassified item.

Known classification commands the selector angle, waits 700 ms, opens the gate for 600 ms, then commands closed for 400 ms. The command counter increments, the selector returns home for 700 ms, and WAIT_CLEAR requires absence for 300 ms. If WAIT_CLEAR lasts 5 seconds, the cycle faults. There is no independent item-exit sensor: a clear presence detector does not prove the object reached the right bin.

No `delay()` is used in the cycle state machine. Servo pulses are generated by the library. Actual loop/servo timing and mechanical travel need physical measurement. Time comparisons use unsigned subtraction for millis wraparound. A stop/fault commands gate closure while retaining selector position; this is software behaviour, not a certified safety function or position confirmation.

The implementation assumes a single retained item and two actuators. It does not reproduce an unspecified DC motor/conveyor design. Optional gate endpoint feedback is now implemented, disabled by default. Absolute selector homing, torque/current measurement, item-exit confirmation, automatic jam clearing, persistent on-device logs and network output remain absent.


## Fault provenance and optional gate watchdog

The controller retains the first fault cause until R clears it: 0=none, 1=stop loop, 2=lost item, 3=invalid ADC, 4=ambiguous sample, 5=chamber-clear timeout, 6=gate endpoint feedback. The first cause is a software observation, not a proven physical root cause. X commands a stopped/closed output but does not bypass an existing FAULT.

`GateWatchdog` compares the requested gate direction with D5/D6 endpoint contacts. Both contacts active is contradictory and faults immediately. Neither endpoint is allowed during travel; if the requested endpoint is still absent at or after 350 ms, the fault latches. Once that deadline has passed, losing the endpoint also faults. A contact observed at the deadline is accepted; loop sampling cannot establish the exact physical arrival time. Unsigned time subtraction covers millis rollover. Contacts are not debounced in software, so bounce/electrical noise needs separate validation/filtering.

The sketch commands gate closure on a feedback fault. It cannot guarantee closure of a blocked actuator or isolate its power. Reset requires physical closed indication and the other existing conditions. Default false leaves the original two-servo timing behavior except for the fault-latch fix and telemetry. The current circuit SVG shows baseline wiring; optional contacts are documented separately in wiring.md.
